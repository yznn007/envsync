# ADR-0001：在 domain crate 内自实现严格 canonical CBOR 编解码器

**日期：** 2026-07-26

**状态：** 已接受

**相关计划：** `docs/superpowers/plans/2026-07-24-envsync-m0-safe-file-loop.md` 任务 3

## 背景

M0 计划把 `minicbor` 列入技术栈，用于对象编码。设计文档同时提出两条硬性要求：

- §3.3：「编码使用严格版本化的 canonical CBOR。未知格式版本必须拒绝，不能静默降级。」
- M0 任务 3：「非 canonical CBOR、未知版本和摘要不匹配均被拒绝」「解码后重新编码并比较，
  拒绝非 canonical 表示」。

通用 CBOR 库（含 `minicbor`）的解码器出于兼容性考虑，会**接受**多种等价表示：不定长度
编码、非最短整数编码、任意 map 键顺序、重复键。它们只保证「编码端是确定性的」，不保证
「解码端拒绝非确定性输入」。而 EnvSync 的内容寻址存储恰恰依赖后者：只要存在两种字节序列
解码为同一逻辑对象，攻击者就可以构造摘要不同、语义相同的对象，绕过基于摘要的去重、
校验与反回滚检查。

## 决策

在 `envsync-domain::cbor` 中实现一个受限的 canonical CBOR 子集，**同时**作为编码器和
校验型解码器使用，不引入 `minicbor` 依赖。

子集规则：

1. 只允许确定长度编码，遇到 additional info `31` 立即拒绝；
2. 整数必须最短编码，`0x18 0x00` 之类的冗余形式被拒绝；
3. map 键按其 canonical 编码字节严格升序，重复键被拒绝；
4. 不支持浮点数、tag、`undefined` 及其他 simple value——这些在领域模型中没有用途，
   排除它们同时消除了浮点数在跨平台上的不确定性；
5. 解码设深度上限 64、节点上限 4,000,000，并在分配前校验声明长度不超过剩余输入；
6. 顶层解析后若有剩余字节则拒绝。

结构体统一编码为 CBOR **数组**（字段顺序即声明顺序），语义 map 才使用 CBOR map。
`decode_canonical` 在解码后额外做一次「重新编码必须逐字节相同」的断言，作为纵深防御。

## 后果

**正面：**

- 「解码成功」即蕴含「输入是唯一 canonical 表示」，内容寻址的唯一性由类型系统之外的
  解析层强制保证；
- 减少一个第三方依赖，缩小供应链攻击面（对一个以同步凭据为目标的工具而言，这一点
  尤其重要）；
- 错误类型完全由本项目定义，可以携带精确的机器可读错误码，满足 CLI JSON 契约要求。

**负面：**

- 需要为每个领域类型手写 `CborCodec` 实现。已通过 `cbor_struct!` 与 `cbor_unit_enum!`
  两个声明宏把样板代码压到最小；
- 不支持浮点数意味着未来若要同步浮点配置值，必须显式选择定点或字符串表示。这被视为
  优点而非缺陷：浮点数的跨平台字节表示本就不适合进入内容寻址存储。

## 备选方案

- **`minicbor` + 解码后再编码比较**：仍需自己实现 canonical 校验逻辑，且无法阻止在
  比较之前就已经发生的重复键覆盖等语义损失。收益不足以抵消额外依赖。
- **`ciborium` / `serde_cbor`**：前者不保证 map 键排序，后者已停止维护。

## 影响范围

`envsync-domain::cbor`；所有实现 `CborCodec` 的领域类型。不影响 CLI 的 JSON 输出
（JSON 契约仍使用 `serde` + `serde_json`）。
