# ADR-0003：Plan ID 绑定输入而不绑定生成时刻

**日期：** 2026-07-26

**状态：** 已接受

**相关计划：** M0 任务 7、任务 11

## 背景

设计文档 §3.4 写「Plan ID 由上述完整内容确定」，其中「上述」列举了目标快照、Ref
revision、观察结果、动作、风险与回滚能力。M0 任务 11 又要求：

> `sync` 只接受 Plan ID；重新生成不一致时返回 stale plan。

这一新鲜度检查的实现方式是：应用前重新观察、重新生成计划，比较新计划的 ID 与用户
提交的 Plan ID。如果 `Plan` 的时间戳字段参与 ID 计算，那么**任何**重新生成都会得到不同
的 ID，`sync` 将 100% 返回 stale plan，命令面完全不可用。

## 决策

`Plan` 结构体保留 `created_at_unix_ms` 字段用于审计与展示，但它**不参与** `Plan::id()`
的计算。参与计算的绑定内容为：格式版本、工作区、设备、目标快照、base revision、
待写入的下一个 Ref、全部观察结果、全部动作、全部诊断。

编码上，`Plan` 序列化为 `[binding, created_at]` 两元数组，`binding` 子数组即 ID 的原像。
这样「ID 覆盖什么」在编码结构上一目了然，不依赖注释约定。

## 补充（2026-07-26 晚，实现期发现）

第一版实现只排除了 `Plan::created_at_unix_ms`，却把 `observations` **整体**编入原像，
而 `Observation::observed_at_unix_ms` 同样是每次重新观察都会变的时刻。结果是：跨进程的
`plan` → `sync` 只要不在同一毫秒内完成，Plan ID 就不同，新鲜度检查 100% 判定 stale——
正是本 ADR 想要避免的失效模式，只是换了一个字段。核心层的测试注入了固定时钟，恰好把
这个缺陷完全掩盖，直到 CLI 的端到端测试真正跨进程跑了一遍才暴露。

因此本决策修订为：**原像绑定观察的内容，不绑定观察的时刻**。实现上，`Plan::id()` 使用
`id_preimage()`，它把每条观察的 `observed_at_unix_ms` 归零后再编码；`Plan::to_value()`
仍然保留真实时刻，序列化往返无损。回归测试见
`envsync-domain::plan::tests::plan_id_ignores_observation_timestamps`。

一般化的规则：**任何"每次运行都会变、且不代表状态差异"的字段都不得进入 Plan ID 原像。**
判据是「如果这个字段变了，用户是否需要重新审阅这份计划？」——时刻不需要，内容摘要需要。

## 后果

- `sync` 的新鲜度检查成为一个纯粹的等价性判断：只要目标快照、后端 revision、本机
  观察结果、动作集合中任何一项变化，Plan ID 就变化，计划立即失效；
- 两次在不同时刻、相同条件下生成的计划 ID 相同，因此计划可以被保存、传输、在桌面端
  审阅后再应用，而不会因为「审阅花了三分钟」而失效；
- 诊断参与 ID 计算：诊断是输入的确定性函数，把它纳入绑定可以防止「同样的动作集合但
  阻塞原因不同」被误判为同一计划。

## 影响范围

`envsync-domain::plan::Plan`；`envsync-core` 的 `build_plan` 与 `apply_plan`;
CLI `sync --plan <plan-id>`。
